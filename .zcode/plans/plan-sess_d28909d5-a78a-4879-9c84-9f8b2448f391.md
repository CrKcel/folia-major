# 端侧 AI 主题生成：node-llama-cpp 本地 provider

## 背景结论

应用的 AI 主题生成链路已经存在（`generate-theme` IPC → `electron/aiTextClient.cjs` 的 `runAiJsonCompletion` 按 `AI_PROVIDER` 分发到 Gemini / OpenAI 兼容端点 → `shared/themeSanitizer.cjs` 净化产出 DualTheme）。歌词分词（`segment-lyrics`）也走同一分发函数。本方案是把 **本地 node-llama-cpp** 作为第三个 provider 接入分发层，主题生成与歌词分词同时生效；模型由用户手动指定本地 .gguf 路径，无应用内下载。

## 架构

仿照 `electron/analysis/`（onnxruntime worker 先例）：node-llama-cpp 跑在独立 `utilityProcess` worker 里，不进 main 进程——模型占几百 MB 内存、推理耗时长、原生库崩溃不能拖垮主窗口。main 进程代码不动 `main.cjs` 的新逻辑禁区。

```
renderer (设置: 选 .gguf / 测试)
   │ IPC
   ▼
main.cjs generate-theme / segment-lyrics（现有 handler）
   │ runAiJsonCompletion → provider === 'local' 分支（新增）
   ▼
electron/llm/host.cjs（新）—— spawn/复用 worker、请求关联、空闲回收、硬超时
   │ utilityProcess.fork
   ▼
electron/llm/worker.cjs（新）—— node-llama-cpp 加载 .gguf，
   createGrammarForJsonSchema(schema) 约束输出为合法 JSON
```

关键点：JSON Schema → GBNF 语法约束是小模型可靠产出 DualTheme JSON 的核心，主题 schema（`THEME_JSON_SCHEMA`）和分词 schema 都直接传入。

## 文件改动

**新增**
1. `electron/llm/host.cjs` — 单例 LLM host，仿 `analysis/host.cjs`：首次请求懒 spawn worker，按请求 id 关联应答；空闲 120s kill 回收内存；单请求硬超时 300s（本地 CPU 推理比云端慢，超时后 kill + 下次重启 worker）；worker 崩溃时 reject 所有 pending。对外暴露 `runLocalJsonCompletion({ store, systemPrompt, sourcePrompt, schema, maxTokens })`，内部从 electron-store 读 `LOCAL_LLM_MODEL_PATH`，未配置时抛出与 `GEMINI_API_KEY is not configured` 同风格的明确错误。同时包含 `registerLlmIpc({ ipcMain, store })`：注册 `choose-local-llm-model`（`dialog.showOpenDialog` 过滤 `.gguf`）和 `test-local-llm`（发一条极短 prompt 返回延迟或错误，供设置页"测试"按钮）两个 IPC。
2. `electron/llm/worker.cjs` — `getLlama()` → 加载 store 传入的模型路径 → 每个请求用 schema 建 grammar，chat completion 返回 JSON 文本。固定常量：contextSize 8192（歌词 2000 字符 + system prompt + 输出余量）、温度读现有 `OPENAI_API_TEMPERATURE` 设置。模型加载失败/非 gguf 文件给出可操作的错误信息。

**修改**
3. `electron/aiTextClient.cjs` — `runAiJsonCompletion` 增加 `provider === 'local'` 分支委托给 host。`generate-theme` 与 `segment-lyrics` 两个 handler 自动生效，main.cjs 几乎不用动。`disableReasoning` 在本地 provider 下为 no-op（推荐用户用 instruct 模型）。
4. `electron/main.cjs` — 最小改动：`generate-theme` handler 里为 local provider 设置 `dualTheme.*.provider = '本地模型 (node-llama-cpp)'` 标签；启动处调用一次 `registerLlmIpc`。
5. `electron/preload.cjs` + `src/vite-env.d.ts` — 暴露 `chooseLocalLlmModel`、`testLocalLlm`（仿现有 `choose-models-directory` 模式）。
6. `src/components/modal/settings/DesktopSettingsSubview.tsx` — `AI_PROVIDER` 增加本地模型选项；选中时显示：当前模型路径 + 选择按钮（调 `chooseLocalLlmModel`）+ 测试按钮（调 `testLocalLlm`，显示延迟/错误）。若该文件过长，按 file-modularization 拆出 `LocalLlmSettingsSection.tsx`。
7. i18n 三个语言文件（en / zh-CN / in）补齐新增文案；命令面板如有 AI provider 相关命令则同步更新（`src/components/command-palette/commands/settingsCommands.ts`，用现有 `createSettingsCommand` 工厂）。
8. `package.json` — `node-llama-cpp` 加入 `dependencies`（main 进程运行时依赖）；`build.asarUnpack` 增加 `node_modules/@node-llama-cpp/**` 与 `node_modules/node-llama-cpp/**`（官方 Electron 要求，二进制必须解包出 asar）。
9. `build/afterPack.cjs` — 扩展现有 `pruneOnnxRuntimeBinaries` 逻辑：删除非目标平台的 `@node-llama-cpp/<platform>` 二进制包，控制安装体积。

**不改动**：renderer 的生成入口（`src/services/gemini.ts`、`useThemeController`、`useSongThemeAutoGeneration`）——provider 选择完全在 main 侧，这些文件无感知。主题缓存、外观导入导出、sanitizer 均复用现状。

## 已知取舍

- 不做应用内下载、不内置推荐模型（按你的选择）：用户需自备 .gguf（Q4_K_M 级小模型即可，语法约束下 1.7B 也能稳定出 JSON）；设置页文案给出格式要求提示。
- 本地 provider 不支持 `disableReasoning`，推理模型可能出现空回复——错误信息会指向"换 instruct 模型"。
- 主题生成的 `USE_SYSTEM_PROXY_FOR_AI` 逻辑对本地 provider 无效，不影响。

## 验证

1. `npm run typecheck` + 现有单测（命令面板 i18n 契约测试必须过）。
2. 为 `runAiJsonCompletion` 的 local 分发补一个单元测试（mock host）。
3. 手动验证：dev 启动 Electron → 设置选择本地 .gguf → 测试按钮通过 → 断网状态生成 AI 主题 → 断网跑歌词分词 → 空闲 2 分钟后确认 worker 进程被回收（任务管理器看内存回落）。
4. `npm run build:electron` 确认 electron-builder 打包后 asar.unpacked 内二进制存在且应用可启动（linux 包）。
